# Capacity Planning for LLM Inference: GPU Memory, Throughput, and SLAs

Capacity planning for LLMs is fundamentally a memory problem. If you don't understand your [KV cache requirements](/blog/serving-open-source-llms-with-vllm-kubernetes), you'll either over-provision and waste [infrastructure spend](/blog/ai-infrastructure-cost-optimization) or under-provision and fail your [latency SLOs](/blog/ai-system-slos-non-deterministic-systems). For unpredictable workloads, you might also consider whether [serverless inference](/blog/serverless-inference-can-it-actually-work-for-production-ai-workloads) is a viable alternative to dedicated capacity.

## The Math of GPU Memory

When planning, you must account for:
1. **Model Weights**: ~1.2x the parameter count in FP16 (e.g., Llama 70B needs ~140GB).
2. **KV Cache**: The memory used to store the context for active requests. This scales with context length and [batch size](/blog/batching-strategies-llm-inference-throughput-vs-latency).
3. **Overhead**: System and runtime memory.

## Modeling Throughput and Latency

Once you have the memory footprint, use [load testing](/blog/load-testing-llm-endpoints-why-traditional-tools-dont-work) to find your saturation point. This helps you define your [autoscaling targets](/blog/gpu-autoscaling-right-sizing-inference-clusters) to ensure you stay ahead of demand without overspending.

## Final Takeaway

Capacity planning for LLMs is an iterative process. By combining theoretical memory modeling with empirical load testing, you can build a fleet that meets your performance SLAs while staying within your budget.
