# Prompt Versioning and Rollback: Treating Prompts Like Infrastructure

If you're hardcoding prompts in your application code, you're creating a bottleneck. In production, [prompts are infrastructure](/blog/stop-building-ml-platforms-start-shipping-ml-features). They must be versioned, [tested in CI/CD](/blog/ci-cd-ml-models-testing-beyond-unit-tests), and deployable independently of your application logic.

## Why Version Prompts?

### 1. Immediate Rollback
When a new "optimized" prompt starts causing [hallucinations or regressions](/blog/building-eval-pipeline-catches-regressions-before-users), you need to be able to revert to the previous version in seconds via your [LLM gateway](/blog/llm-gateway-architecture-routing-rate-limits-cost-controls).

### 2. A/B Testing and Canary Rollouts
Versioned prompts allow you to run [canary releases](/blog/model-canary-releases-shadow-traffic-guide) to compare the performance of two different prompt strategies against live traffic using [statistical methods](/blog/ab-testing-llm-outputs-statistical-methods-non-numeric-responses).

### 3. Auditability and Reproducibility
For [regulated teams](/blog/ai-audit-logs-regulators-ask-for-how-to-prepare), you must be able to prove which prompt version was used for a specific decision.

## Final Takeaway

Prompt engineering is a production discipline. By treating prompts as versioned infrastructure, you enable your team to experiment safely, respond to failures instantly, and maintain a clear audit trail for every model interaction.
