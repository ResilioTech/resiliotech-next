# AI Incident Response Runbooks: Production Model Failures

When a traditional service fails, it usually returns a 5xx error. When a model fails, it might continue returning a 200 OK while serving hallucinated, biased, or nonsensical outputs. This makes AI incident response fundamentally different from standard SRE workflows.

To handle these "silent" failures, you need a runbook that connects [observability dashboards](/blog/ai-observability-metrics-dashboards-that-matter) with clear, actionable [SLO targets](/blog/ai-system-slos-non-deterministic-systems).

## Triage: Identifying the Failure Class

Is the failure in the [infrastructure](/blog/why-your-ml-models-fail-in-production)—perhaps a [GPU pod OOMKilled event](/blog/kubernetes-oomkilled-gpu-pods-causes-debugging-prevention)—the data pipeline, or the model weights themselves? Your runbook should provide specific commands for each stage:

```bash
# Check for model-server pod restarts and OOMs
kubectl get pods -n ai-production -l app=model-server --sort-by='.status.containerStatuses[0].restartCount'

# Check for KV cache pressure in vLLM logs
kubectl logs -f deployment/vllm-server | grep "cache_utilization"
```

## Mitigation: Rollback and Failover

Once a failure is confirmed, the immediate goal is to restore service. This often involves [graceful degradation](/blog/implementing-graceful-degradation-ai-features-fallback-strategies-that-work), rolling back to a [previous prompt version](/blog/prompt-versioning-and-rollback-prompts-like-infrastructure) or failing over to a more stable [multi-region cluster](/blog/multi-region-ai-disaster-recovery-failover-playbook).

## Final Takeaway

AI incident response is a muscle that must be trained before the incident happens. By building structured runbooks and automated triage paths, you ensure that your team can respond to model failures with precision rather than panic.
